# Field test: shelf

A test of this guide on a real, middle-size project. One person (the tester, played by Claude Code in a separate session) followed the guide step by step and wrote down what happened.

- Date: 13–14 Sep 2026
- Claude Code version: 2.1.270, model Opus 5, on Ubuntu 24.04
- Guide version: commit `dc2c5a7`
- Test project: `shelf`, a reading list web app (TypeScript, Express 5, `node:sqlite`, Vitest). 25 source files, 2838 lines, 60 tests, CI on GitHub Actions. Private repo `tokyovo/shelf`.
- Change tested: "Reading goals". A user sets a yearly goal for the number of books, and the page shows progress against an even pace.

## Summary

The guide works. One change went through every step, from the first interview to a merged PR, and the result was high quality. The PR met all 50 spec criteria, with evidence for each one, and no old test changed.

The guide also has gaps. A reader who follows it exactly hits these problems:

- `claude --worktree` breaks lint and the Stop hook in the main folder.
- The plan approval dialog starts coding, but the guide wants the build in a new session.
- The Stop hook skipped every check during the build, because Claude committed before each stop.
- An unattended `/goal` stopped at a permission dialog.
- The "spec first" rule in `CLAUDE.md` made one of two evals fail.
- "Stop after 30 turns" limits nothing. The whole build counted as one turn.

Most fixes are small: a line in `.gitignore`, a sentence in the steps, or a change to one hook script. See "Proposed guide changes".

## Findings

### High: following the guide leads to a failure

1. **`claude --worktree` breaks the checks in the main folder.** The worktree is created in `.claude/worktrees/` inside the repo, and git does not ignore that folder. While a worktree session was open:
   - `git status` in the main folder was never clean, so the Stop hook ran the full checks after every turn.
   - `eslint .` scanned 40 files in the worktree and failed with `no-undef` errors, because the ESLint browser globals apply only to `public/**` at the repo root.
   - Fix: add `.claude/worktrees/` to `.gitignore` and to the lint and test ignore lists, or create worktrees outside the repo.
2. **Both "Yes" options in the plan approval dialog start coding in the same session.** The guide wants `PLAN.md` saved and the build started in a new session. Choosing "Tell Claude what to change" and typing "Save the plan as changes/<name>/PLAN.md and stop. Do not write any code." worked: Claude saved the file and wrote no code.
3. **The Stop hook checked nothing during the build.** It ran 5 times, and each run took less than 0.1 s. Claude committed before each stop, so git was clean, and `stop-verify.sh` skips when git is clean. The only real checks were Claude's own runs of the check command.
4. **Screenshots outside the project stop an unattended `/goal`.** The run skill saved screenshots in `/tmp`. Reading them opened "Allow reads outside the working directories?". Answering "No" let the build continue, but Claude quietly skipped its own look at the page. `/add-dir /tmp/shelf-run` with "Yes, for this session" removed the problem without changing global settings.
5. **The "spec first" rule in `CLAUDE.md` stops work that has no change folder.** In the `pages-limit` eval, Claude wrote draft spec files and asked questions instead of coding, so the eval failed. Claude also applied the rule inconsistently: in the `search-case` eval, it coded the bug fix directly.
6. **"Stop after 30 turns" in the `/goal` condition limits nothing.** The whole 37-minute build counted as 1 turn.

### Medium: a step or a warning is missing

7. **The Stop hook runs the full checks after turns that change only Markdown.** Writing `INTENT.md` and `SPEC.md` made git dirty, so each writing turn waited for lint, typecheck, and tests. One such run took 69 s.
8. **The test protection hook can shape the design.** `INTENT.md` allowed new fields in `GET /api/stats`. An old test compares the whole stats response, and the hook blocks edits to old tests. So Claude designed a new route instead. It explained this and asked the person to check it.
9. **The guide has no branch step.** It does not say which branch the change files go on. `--worktree` starts its branch from the current branch, not from `main`.
10. **Step 1 copies the whole template folder.** Empty `SPEC.md` and `PLAN.md` templates then sit in the change folder before their steps.
11. **Plan mode saves its draft in `~/.claude/plans/`.** The draft is not in the repo, so saving `PLAN.md` is a required step.
12. **Pushing a CI file change needs the `workflow` scope.** The first push failed with "refusing to allow an OAuth App to create or update workflow". `gh auth refresh -s workflow` did not add the scope on this machine. An SSH remote avoided the problem.
13. **`/sandbox` on Linux needs `bubblewrap` and `socat`.** `socat` was missing, and installing it needs `sudo`.
14. **`/run-skill-generator` is slow and machine-specific.** It took 12.5 minutes. The skill it wrote contains an absolute browser path, a port that was free only on this machine, and `CONTAINER=1` for this Ubuntu version.
15. **`verify-app` is the largest cost.** Its browser checks took about half of the build time (18 min and 5 min in two runs).
16. **The eval runner needs changes.**
    - Eval runs leave branches in the repo, because the eval's Claude creates branches.
    - The copied setup files keep git dirty in each eval worktree, so the Stop hook runs at every stop.
    - Hidden tests kept inside the repo can be found by the test config, and any session can read them.
    - A full-loop eval takes about 4 minutes, so 20–50 tasks take 1.5–3.5 hours.
17. **Prompts that wait for a person:**
    - a "Do you trust this folder?" dialog in a new folder
    - "Teach auto mode about your environment?" after the first auto mode turn
    - the read permission dialog from finding 4
18. **The token number in the `/goal` status line is not the real cost.** It showed 152.1k. The transcript shows 454k output tokens.

### Low: small fixes

19. **Suggested replies appeared in the input box 5 times.** One was false at that moment ("I updated SPEC.md with the error text, go ahead"). A careless Enter would send it.
20. **The `loop.md` rule about changes the spec does not cover worked, but it adds work for small comments.** A wording comment became a spec edit by the person, plus one more 30-minute wait.
21. **The spec and the plan are long to review (184 and 309 lines).** The guide gives no review checklist. A fact check of the plan found one wrong line number.
22. **Example files need small fixes.**
    - `CLAUDE.md` has placeholder lines that fit few projects, and no hint about another port.
    - `REVIEW.md` names a `generated/` folder.
    - The copy step does not add `evals/results/` to `.gitignore`.
    - `TEST_PATTERN` also matches `tests/helpers.ts`.
    - `origin/HEAD` is not set after `gh repo create`.
23. **Plain `claude` uses the reader's default permission mode.** On this machine that default is auto mode, so step 1 did not ask for permissions.

### What worked well

- **The interviews.** Claude read the code before it asked. It asked one question at a time, often as a multiple-choice dialog with a recommended answer and a worked example.
- **Skills.** Claude applied `api-security` and `run-shelf` without being asked. They became acceptance criteria and verify steps.
- **Catching problems.** A review correction made two criteria impossible to check, and Claude found them. In plan mode, it found that the existing year parser accepts `0x7EA`.
- **The build followed the plan.** The commit changed exactly the files that the plan listed and added 3 test files. No old test changed.
- **The PR description.** It mapped all 50 criteria to evidence: test names, smoke checks, browser checks with values and screenshot names, and the reviewer. The final message had every item that the `/goal` condition asked for.
- **The reviewer.** It found a real Nit (the page did not use the server's year). Claude fixed it in its own commit. Claude also waited for `verify-app` to finish before it edited files.
- **`/loop`.**
  - It followed `loop.md` exactly. It did not code a change that the spec did not cover. It never replied on GitHub, never pushed to `main`, and never merged.
  - It sent a push notification when the PR was ready and when the loop stopped.
  - It stopped by itself after the merge.
- **The test protection hook.** In a live session, it blocked an edit to an old test. Claude did not try to go around the hook, and it explained why the test matters.
- **Testing the real app.** `/run-skill-generator` found a bug that unit tests missed: the tag input's `pattern` attribute logs a console error on every page load.

## Guide changes

These changes were applied to the guide on 14 Sep 2026, in the same commit as this report. The numbers point to the findings above. The new Stop hook and the new eval runner were tested only in scratch repos, not in a live run. See `docs/open-questions.md`.

### `README.md` and `docs/summary.html`

- Setup steps:
  - Add `.claude/worktrees/`, `evals/results/`, and the screenshot folder to `.gitignore` and to the lint and test ignore lists. (1)
  - Step 3: say that `/run-skill-generator` can take more than 10 minutes. Review the skill for machine-specific paths before you commit it. (14)
  - Step 6: on Linux, `/sandbox` needs `bubblewrap` and `socat`. (13)
- For each change:
  - Add a first step: create a branch for the change from `main`. (9)
  - Step 1: copy only `INTENT.md`. (10)
  - Step 3: in the plan approval dialog, choose "Tell Claude what to change" and type the save-and-stop text. Say that plan mode keeps its draft outside the repo. (2, 11)
  - Before `/goal`: run `/add-dir` for the screenshot folder, or keep screenshots inside the project. (4)
  - Add a short review checklist for the spec and the plan. (21)
- Add a rule for which work needs the full INTENT → SPEC → PLAN flow. For example: new behavior needs it, and a bug fix with a failing test can go straight to `/goal`. (5)
- Watch out:
  - Replace the turn limit advice. (6)
  - The `/goal` token number is not the real cost. (18)
  - `verify-app` is the largest cost. (15)
  - Do not press Enter on a suggested reply. (19)
  - List the prompts that wait for a person. (17)
  - The test protection hook can shape the design, and `ALLOW_TEST_EDITS=1` exists for a spec that changes an old contract on purpose. (8)

### `examples/.claude/hooks/stop-verify.sh`

- Skip only when the tree is clean **and** `HEAD` is the last commit that passed. Store that commit next to the counter file. (3)
- Skip when only `changes/**` or other Markdown files changed. (7)

### `examples/CLAUDE.md`

- Limit the "spec first" rule to new behavior. Say what a bug fix needs instead. (5)
- Show how to use another port. Mark the placeholder lines to delete. (22)

### `examples/.claude/loop.md`

- Keep the rule about changes the spec does not cover. Add: "When a person updates SPEC.md, make the change on the next check." (20)
- Say that a push notification is a good way to tell the person that the PR is ready.

### `examples/evals/`

- `run-evals.sh`:
  - Add to each prompt: "No change folder is needed. Stay on the detached HEAD. Do not open a PR." (5, 16)
  - Delete the branches that a run creates. (16)
  - Keep the copied setup files from making git dirty. For example, commit them in the worktree first. (16)
- `README.md`:
  - Show the "hidden test next to `check.sh`" pattern.
  - Keep tasks out of test discovery.
  - Give the time estimate. (16)

### `examples/README.md`

- Copy step: add the `.gitignore` lines. (1, 22)
- `gh`: pushing a CI file change needs the `workflow` scope. An SSH remote avoids the problem. (12)
- "What to change":
  - `TEST_PATTERN` also matches test helper files.
  - Run `git remote set-head origin -a` if `origin/HEAD` is missing. (22)
- The `/goal` condition: drop the turn clause. End with "If you cannot finish, stop and list what is left." (6)
- Parallel sessions: start each worktree from `main`, and ignore `.claude/worktrees/`. (1, 9)

### `docs/open-questions.md` and `docs/sources.md`

- Tick the questions that this test answered:
  - `/run-skill-generator` works when typed.
  - `protect-tests.sh` blocks a real edit.
  - The turn limit in `/goal` is not a real limit.
  - `/loop` with `loop.md` stops by itself after the merge.
- Record the `/loop` cost while the PR is quiet: the merge check took 23 s.
- Add this field test as the source for the measured numbers.

## Limits of this test

- One project, one change, and one run of each step. The numbers show one example, not an average.
- The tester was Claude Code, not a human. The tester answered questions, reviewed files, and merged, but a human reviewer may catch different things.
- The tester drove the sessions through tmux (`tools/drive.sh`). Three problems came from this method, not from the guide:
  - one lost Enter key
  - one dialog answer that the tester did not see
  - one Down key that did not register in a dialog with a preview
- The machine had the user's global skills installed (for example, a headless browser tool). The run skill used them.
- `/sandbox` was not tested, because `socat` was missing.
